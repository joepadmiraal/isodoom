# Netgame freezes on wifi: follow-up tasks (for M11 in `docs/TASKS.md`)

Found 2026-10-18 while testing a Linux laptop against a Windows laptop on a home LAN, both on good wifi, pinging each other at 5–100 ms. The game froze often. No code was changed; this is a reading of the netcode (`NetClient`, `NetServer`, `NetSession`, `NetEnetTransport`, `LevelScene.Net`).

**Why it freezes.** A tic runs only once its bundle came and the game clock reached it (`RunNetTics` → `NetClient.TryTakeTic`); otherwise the world holds. A join's command for tic T leaves at about clock T − delay, goes to the host, and comes back in the bundle, so the delay must cover a whole round trip plus the frames' polling. Today:

1. **The delay is fixed at the start, from one ping.** `NetSession` takes `NetOptions.DelayFromRtt(slowest RTT)` = ⌈RTT / 28.6 ms⌉ + 1, where the RTT is `NetServer.RttUsOf(slot)`: the client's *last* ping report. A 5 ms sample gives delay 2 (57 ms) for the whole game; any round trip above about 30–50 ms then holds the world.
2. **Polling once a frame eats the margin.** Commands are built, and ENet serviced, once a frame (`PollNet` at the start of `_Process`): the command made up to a frame late, the host seeing it on its next frame, the join seeing the bundle on its next: up to about 50 ms at 60 fps, more under vsync or a slow frame, against the rule's one tic (28.6 ms) of slack.
3. **Every command and bundle is reliable and ordered, sent once** (`NetMessages.cs`: channel 0, `FlagReliable`). A packet lost on wifi blocks everything behind it until ENet resends it, after about RTT + 4 × its variance: 150–400 ms on a jittery link. That is a freeze whatever the delay.
4. **The measurements didn't see it.** `NetMeasurementTests` runs `MemoryTransport` with 5 ms of jitter each way; home wifi (power saving on the adapters) swings by 100 ms.

Quick checks before any code: the host's log line `Net: round trips: slowest X ms: delay N tic(s)` (expect N = 2–3); the F3 overlay's `net:` line (stalls in the last second against the pings); `-netdelay 6` on the host (should stop most of causes 1–2); wifi power saving off (Windows: the adapter's power saving mode; Linux: `iw dev wlan0 set power_save off`) or one machine on ethernet.

## Tasks

- [ ] **T11.12a A default delay that survives wifi jitter (from T11.12's LAN test).** The default delay comes from one ping (`NetServer.RttUsOf`: the client's last report) and allows one tic for the frames' polling, so a game started on a 5 ms sample plays at delay 2 and holds whenever the round trip passes about 30–50 ms. Keep each slot's recent round trips on the server (the pings of the lobby and of `NetSession.RttWaitUs`'s wait, at least 20 samples), take a high percentile (p95) or the maximum of them, and add two frames' worth of slack instead of one tic (say ⌈(RTT + 2 frames) / tic⌉ + 1, at least 3 tics), still clamped to `NetOptions.MaxDefaultDelay`; log the samples' spread with the delay. Update SPEC §12's T11.6 "Default input delay" and T11.12's measured delays.
  *Done when* a `MemoryTransport` test with 5–100 ms of jitter each way (a burst of 100 ms spikes, not just uniform) runs a minute of play with no stall after the first second, and the delay picked there is logged; `NetMeasurementTests`' delays are updated.

- [ ] **T11.12b The delay adapts in the game (after T11.12a).** The delay is fixed for the whole game, so a link that gets worse after the start (wifi, another device on the network) stalls until the end. Let the host change it: it watches the players' round trips and the stalls (the clients' late tics, sent with the checksum reports or the pings), and announces a new delay that takes effect at a future tic every machine knows of (a `Delay` message, the protocol's version bumped): raising it inserts empty commands for the tics between, lowering it (slowly, after a calm spell) drops the client's surplus. The sim sees only commands, so determinism is unchanged; the overlay's `net:` line shows the delay as it moves. Chocolate Doom keeps a fixed delay too; this is ours (SPEC §12 entry).
  *Done when* a `MemoryTransport` test whose link goes from 10 ms to 120 ms round trips mid-game stalls for at most a second, then plays on without stalls at the raised delay, and comes back down when the link does; the lockstep tests stay in sync.

- [ ] **T11.12c Commands and bundles without head-of-line blocking (from T11.12's LAN test).** Every command and bundle goes on ENet's reliable, ordered channel, sent once, so a packet lost on wifi holds every later one until ENet resends it (RTT + 4 × variance: hundreds of ms on a jittery link): a freeze whatever the delay. Send them unreliable, as Chocolate Doom does (net_client.c / net_server.c): each client's packet carries its commands from the last one the server acknowledged (in every bundle) up to the newest, and each bundle carries the tics from the last one that client acknowledged (in every command packet) up to the newest, so one lost packet costs nothing and a burst costs a round trip; resend on a timer when nothing new goes. Keep the lobby, the Start, the checksums, the quits and the desync on the reliable channel. Bound the packets (`MaxTicsPerMessage`) and say what happens when a peer falls further behind than the ring (`BackupTics`).
  *Done when* a `MemoryTransport` test with 5 % unreliable loss (and a loss burst) at 30 ms round trips plays a minute with no stall longer than one round trip, in sync; the loopback tests (exchange, play, `--kill`, `--desync`, `test-cross`) pass; `NetMeasurementTests`' bandwidth is updated (the redundancy costs some).

- [ ] **T11.12d The network polled more than once a frame (from T11.12's LAN test).** ENet is serviced and the commands built only at the start of each frame (`PollNet`), so each hop waits up to a frame: up to about 50 ms on a round trip at 60 fps, more under vsync or a slow frame (a laptop at 30 fps). Service the transport again right after the commands are built and flushed and before the tics are taken, so the host bundles in the frame a command comes and the join runs in the frame a bundle comes; measure whether a network thread of its own (ENet serviced every millisecond, events queued for the main thread; Godot's ENet objects are not thread-safe, so the thread would own them) is worth it beyond that. Recheck the default delay's slack (T11.12a) with the result.
  *Done when* `NetMeasurementTests` (or a new test driving the frames at 30 and 60 fps) shows the felt input delay at a given ping down by about a frame each hop, and the loopback tests pass.

- [x] **T11.12e Jitter and loss in the measurements (from T11.12's LAN test).** `NetMeasurementTests` runs with 5 ms of jitter each way, so nothing caught the freezes home wifi gives (5–100 ms pings between two laptops). Add a wifi profile to `MemoryTransport`'s cases (a low base, spikes of 50–150 ms in bursts, a little loss on both channels) and report the stalls a minute (count, longest, total time held) next to the bandwidth and the delay; record the numbers before and after T11.12a–d in SPEC §12 "T11.12 measurements". Add a line to the player readme's multiplayer section: wifi power saving off, or ethernet, for the smoothest game; `-netdelay N` as the manual fix.
  *Done when* the wifi profile runs in `NetMeasurementTests`, its stall numbers are in SPEC §12, and the readme line is in.

Order: T11.12e first (it measures the rest), then T11.12a (cheap, probably most of the gain), T11.12c, T11.12d, T11.12b. T11.12's people-run LAN and internet checks should be redone after them.

## Other findings from the same test

- [ ] **T11.9f The menus' sessions take the command line's net arguments (from T11.12's LAN test).** A game hosted from the menus (Multiplayer → Host Game) ignores `-netdelay`: `LevelScene.Lobby.cs`'s `HostGame` builds its `NetOptions` from the `net/*` settings only, and `NetOptions.Parse` returns null without `-host` or `-connect`, so `-- -iwad doom2.wad -netdelay 8` started a menu-hosted game at the measured delay (3) without a word. `-nettimeout` and `-bind` are dropped the same way, and Join Game (`NetOptions.Parse(["-connect", address])`) drops `-nettimeout`. Read the session arguments that are not the game's settings (`-netdelay`, `-nettimeout`, `-bind`, `-name` already is) from the command line for the menus' sessions too (a `NetOptions.Overrides(args)` beside `Modes`); log the delay's source (`delay 8 tic(s) (-netdelay)` or the round trips). Decide with the user whether Host Game also gets an INPUT DELAY item (`net/delay`: AUTO, 1–8), so a player without a terminal can set it; it would then be the setting, with `-netdelay` over it for the run (as `--level-*` over the settings).
  *Done when* a menu-hosted game started with `-netdelay N` plays at delay N (a `LobbyMenuTests` or `NetSessionStartTests` case, and the log line), and `-nettimeout` applies to menu hosts and joins.

- [ ] **T11.1b Co-op on Doom II v1.666: the start check refuses every first map (from T11.12's LAN test; see T11.9e).** `-host -players 2` on Doom II v1.666 (`wads/doom2.wad`, MD5 `30e3c2d0…`) logs `Net: the game cannot start: no co-op start for player 2 on MAP29` and never starts: v1.666's MAP29 has player 1's start only (the other IWADs at hand, The Ultimate Doom 2024, TNT, Plutonia, DOOM1, have every map's four), and T11.8's check covers every map the exits can reach, so every first map but MAP30 is refused. A whole IWAD's co-op is lost to one late map. Only deathmatch (first map only) or `--level MAP30` start now. Options for the user to pick (T11.1a was the user's decision, no deviation from vanilla, which crashes in `P_PlayerThink` there):
  1. Check the first map only, as deathmatch does; a later map that lacks a player's start ends the netgame on every machine when the game gets there, with a menu message (as `the netgame ended: MAP28: Only 2 deathmatch spots, 4 required`). Vanilla behaviour kept, the game playable up to MAP28.
  2. As 1, but the lobby warns (not refuses) at the start: `MAP29 lacks player 2's start: the game will end there`.
  3. A tweak (SPEC §6.3): a player without a start spawns at another player's co-op start (the first free one by `G_CheckSpot`, else at player 1's start). Not vanilla, so behind a named flag, off in the vanilla tests; the netgame plays through.

  Whichever is picked, the level check's multiplayer section on Doom II (T11.9e's 8 failures) follows it, and the player readme says what happens.
  *Done when* `-host -players 2` on Doom II v1.666 starts a co-op game on MAP01 and what reaching MAP29 does is the option picked, tested (`NetStartsTests`, and a route or level-check case at MAP29), and in SPEC §12.
